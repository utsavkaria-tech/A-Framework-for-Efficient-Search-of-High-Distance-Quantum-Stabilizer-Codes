# Reproducing the results

Three independent pipelines. None depends on the others; run whichever you need.

## 1. Correction-factor analysis (Sections 4.1, 4.2)

### 1a. Build the cache (once, ~20-40 min of network time)

`codetables_cache.sqlite` (167 MB) is not committed. Rebuild it:

```bash
cd 01-code-tables-analysis/src
python qecc_pipeline.py --q 2 3 4 5 7 8 --n-min 1 --n-max 256 --rps 6
```

The fetch is rate-limited, retrying, resumable and never re-downloads a URL. It writes the
cache next to the script. Everything after this point is offline.

Useful flags:

| Flag | Default | Effect |
|---|---|---|
| `--skip-fetch` | off | parse/analyse the existing cache only, no network |
| `--force-reparse` | off | re-parse every cached page |
| `--weight-mode` | `symplectic` | `symplectic` counts coordinates `j` with `(X_j,Z_j) != (0,0)`; `raw` counts non-zero symbols across all `2n` columns |
| `--x-sum-mode` | `distinct` | sum `X` over distinct weights (`rows` weights each term by its frequency `f_i`) |
| `--rps` | 6.0 | requests per second |

**Expected output** (matches `results/reports/run_summary.txt`): 58,902 sets examined,
34,775 processed, 24,127 skipped, 1,909 semi-perfect, elapsed ~22 s for the offline phases.

### 1b. Run the three analyses

```bash
python analysis_scaling.py                # -> analysis/, Summary/SCALING_ANALYSIS.md
python analysis_semiperfect.py            # -> analysis/, Summary/SEMIPERFECT_ANALYSIS.md
python analysis_Cprime_semiperfect.py     # -> analysis/, Summary/CPRIME_SEMIPERFECT_RESULTS.md
```

Each script recomputes every number from the SQLite cache — nothing is carried over
between runs. Outputs land in `analysis/` (CSV + plots) and `Summary/` (reports); in this
repository those are checked in under `results/fits`, `results/workbooks`,
`results/reports` and `figures/`.

### 1c. The ML estimate of `C'` (Table 4.2.3, first column)

```bash
python correction_factor_estimator.py     # edit `q = 2` at the top for other field sizes
```

Cross-validated KNN / Random Forest / Extra Trees / Gaussian-process regressors predicting
`C'` from `(n, k)` on semi-perfect codes only. **This script reads
`Excel Files/all_codes_combined.csv` via an absolute Windows path** — change the `pd.read_csv`
path near the top to `../data/all_codes_combined.csv` before running it elsewhere.

Turning an estimated `C'` into a weight spectrum and a runtime speedup is the manual
procedure in Supplementary §1.8.3; it is not scripted.

## 2. Runtime benchmark (Section 4.3)

Four independent engines, one per constraint. All share the same CLI.

```bash
cd 02-runtime-benchmark/src

# A - unconstrained baseline
python stabilizer_search_benchmark.py --n 5 --k 1 --d 3 \
    --constraint none --backend numpy --target span --work 5 --repetitions 2

# B - universal stabilizer constraints (rank + symplectic commutation)
python stabilizer_search_benchmark_universal.py --n 5 --k 1 --d 3 \
    --constraint universal --backend numpy --target span --work 5 --repetitions 2

# C - weight spectrum W = {4}
python stabilizer_search_benchmark_weight4.py --n 5 --k 1 --d 3 \
    --constraint weight --weights 4 --backend numpy --target span \
    --work 5 --r0-start 128 --r0-count 128 --repetitions 2

# D - cyclicity (constructive generation, not filtering)
python stabilizer_search_benchmark_cyclic.py --n 5 --k 1 --d 3 \
    --constraint cyclic --mode generate --backend numpy --target span \
    --work 5 --repetitions 200
```

Every engine ships a self-test: add `--self-test` to check it against independent brute
force at `--work 1, 2, 5`.

### Three things to know before quoting these numbers

1. **Rows A-C are extrapolations.** The full `2^40` space was not traversed. Each figure is
   a bounded sample over a contiguous deterministic region of the same lexicographic
   enumeration, scaled by the exact ratio of candidate counts. Sample sizes: A `1/1024`,
   B and C `1/8` each.
2. **Row D is methodologically different.** Cyclicity uses constructive generation — every
   first row is enumerated and the rest are generated by shifts, with no cyclicity test
   afterwards. It is a complete measurement of 1,024 candidates, not an extrapolation.
   Under the same traverse-and-test methodology as A-C it measures 0.235 s instead of
   0.000227 s. **State this wherever the number is used.**
3. **Weight-4 needs a sampling correction.** Weight-4 row values are not uniformly
   distributed over contiguous ranges of the row alphabet, so the estimate is scaled by
   `global density / region density = 1.0546875`. Raw uncorrected estimate: 343.15 s.

Absolute runtimes were taken as minima over interleaved repetitions on a machine with
intermittent background load (OneDrive sync on the working directory; spreads up to 21%).
**Ratios were stable throughout; for publication-grade absolute timings, re-run on a quiet
machine with the working directory outside any sync folder.** Full methodology, the
per-candidate cost decomposition and 8 validation invariants are in
[`../02-runtime-benchmark/RESULTS_SUMMARY.md`](../02-runtime-benchmark/RESULTS_SUMMARY.md).

## 3. The 14-qubit search (Section 5)

### 3a. Build

```bash
cd 03-search-14-qubit
make -f build/Makefile          # builds stab14, stab14_ext, stab14_2stage
sh build/build_gcc.sh           # same three, explicit g++ invocation
```

On Windows with MSVC, the `build/*.bat` files call `vcvars64.bat` and then `cl`. They
assume Visual Studio is at `C:\Program Files\Microsoft Visual Studio\18\Community\...` —
edit that line for your install. Each `.bat` builds one program; run them from a directory
containing the corresponding source.

The extra programs (`stab14_refine`, `stab14_6opt`, `stab14_kopt`, `staged_search`,
`hitset14`, `reverse_8w10_3w8`, `diag_usable`) are built by their own scripts in `build/`
and follow the same flags.

### 3b. Stage 1 + Stage 2 (the main pipeline)

```bash
./stab14_2stage --mode hybrid
```

- **Stage 1** solves exhaustively in well under a second and is a **proven global
  optimum**: 3 weight-8 generators detecting 80,584 of 91,770 weight-<=4 errors. It
  enumerates the complete optimal family, which reduces to 45 inequivalent orbits.
- **Stage 2** freezes each orbit and searches for 8 weight-10 generators maximising
  coverage of only the 11,186 errors Stage 1 missed. The full 45-orbit sweep takes about
  19 minutes; the best orbits reach `M_8 = 11,179`, i.e. `M_final = 91,763`.

Useful flags: `--threads`, `--seed`, `--stage2-time-limit`, `--stage1-index N` (run a
single orbit), `--deterministic`, `--selftest N`, `--save-all`.

### 3c. Refinement to the published code

```bash
./stab14_refine --time-limit 2400 --out refine
```

Starts from the orbit-0006 incumbent hard-coded at the top of `stab14_refine.cpp`
(`G3_STR` / `H8_STR`), re-derives `U_3` from scratch, re-verifies the incumbent
(weights, commutation, rank, and a brute-force recount against the algebraic score), then
searches 1-opt, 2-opt and 3-opt neighbourhoods exhaustively over all 2,037,794 weight-10
classes.

**Result:** `M_8 = 11,181`, `M_final = 91,765 / 91,770` (99.99455%), 5 residual undetected
errors with weight profile 0/0/2/3. This is the code in Section 5.2.1.

The run writes only under `--out`; it never reads or modifies the Stage-1/Stage-2
artifacts.

### 3d. Reading the results

Each result file states its own status in the header. The two statuses used:

- `PROVEN GLOBAL OPTIMUM` — a completed branch-and-bound with admissible bounds.
- `BEST KNOWN - OPTIMUM NOT PROVEN` — everything Stage 2 and beyond.

The strongest statement about the final code is in
`results/04-final-code/refinement_report.txt`: it is optimal against every 1-generator and
every 2-generator replacement, exhaustively. No impossibility claim is made beyond that.

## Determinism

| Component | Deterministic? |
|---|---|
| `qecc_pipeline.py` and the three analysis scripts | Yes — fully deterministic given the cache |
| `correction_factor_estimator.py` | Tree models seeded (`random_state=42`); KNN and GP are deterministic |
| Runtime benchmarks | Candidate counts, retention and checksums are exact and reproducible; **wall-clock times are not** |
| `stab14_2stage` Stage 1 | Yes — exhaustive |
| `stab14_2stage` Stage 2, `stab14_refine` | Seeded heuristics. Pass `--deterministic` for a fixed tie-break; different `--seed` values explore different orbits. The published seeds are recorded in each result file |

The seed-robustness study in `results/05-further-searches/seed-robustness-orbit0006/`
re-runs orbit 0006 across 16 Fibonacci seeds; `M_8 = 11,179` was never exceeded by the
two-stage construction, which is why 11,179 is described as a robust ceiling rather than a
bound.
