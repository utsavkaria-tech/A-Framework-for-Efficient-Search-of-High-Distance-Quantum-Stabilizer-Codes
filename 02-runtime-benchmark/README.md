# 02 — Runtime benchmark: does a smaller search space actually run faster?

Section 4.3 of the paper.

The framework predicts that a constraint with retention factor `R` shrinks the search
space from `S_O` to `S_O^R`, so an exhaustive search should speed up by `S_O^(1-R)`. This
section tests that prediction directly by *measuring wall-clock time* on the `[[5,1,3]]_2`
code under four constraint settings.

The candidate space is a `4 x 10` binary parity-check matrix:
`S_0 = 2^40 = 1,099,511,627,776`.

---

## Results

| Constraint | `R` | Runtime (s) | Measured speedup | Theoretical speedup `S_0^(1-R)` | Efficiency `eta` |
|---|---|---|---|---|---|
| None (unconstrained) | 1.0000 | 13,851.05 | 1.00 (baseline) | 1.00 | 1.00 |
| Universal stabilizer | 0.8469 | 342.99 | 40.38 | 69.69 | 0.5794 |
| Weight spectrum `W = {4}` | 0.8661 | 361.91 | 38.27 | 40.87 | 0.9477 |
| Cyclicity | 0.2500 | 0.000227 | `10^7.7854` | `2^30` | 0.0568 |

`eta` = measured / theoretical. It is always `<= 1` because the theoretical model prices
only the candidates, not the cost of *evaluating* the constraint. The full decomposition,
including per-candidate cost in nanoseconds, is in
[`RESULTS_SUMMARY.md`](RESULTS_SUMMARY.md).

Why the ordering: weight-`{4}` is row-local, so a block of 1,048,576 candidates is accepted
or rejected on two table lookups and the test is nearly free (`eta = 0.95`). The universal
constraint must test 2.10 candidates per accepted one and maintain rank, hence `eta = 0.58`.
Cyclicity processes only 1,024 candidates — far too few to amortise NumPy's fixed per-call
overhead — so its low `eta` reflects that overhead, not the constraint.

## Contents

| File | Experiment |
|---|---|
| `src/stabilizer_search_benchmark.py` | **A** — no constraints (baseline) |
| `src/stabilizer_search_benchmark_universal.py` | **B** — `rank(H) = 4` and `H_X H_Z^T = H_Z H_X^T` |
| `src/stabilizer_search_benchmark_weight4.py` | **C** — every row has Pauli weight 4 |
| `src/stabilizer_search_benchmark_cyclic.py` | **D** — `row_{i+1} = cyclic_shift(row_i, 1)` |
| `RESULTS_SUMMARY.md` | Full results, methodology, validation invariants, exact reproduction commands |

The four engines are deliberately separate files rather than one parameterised program, so
that each constraint's hot loop can be read and audited on its own.

### What these programs are, and are not

They measure the cost of **traversing** a candidate space. There is no sampling inside the
measured region, no heuristic, no counting shortcut, no early exit, no symmetry reduction
and no duplicate elimination. Every candidate in the relevant space is genuinely visited
and processed. They are **not** code-search algorithms and do not impose distance, code
validity or canonical forms.

---

## Three caveats that must travel with these numbers

1. **Rows A–C are extrapolations, not full traversals.** The `2^40` space was not
   exhausted. Each figure comes from a bounded sample over a contiguous deterministic
   region of the same lexicographic enumeration, scaled by the exact ratio of candidate
   counts. Sample sizes: A `1/1024`, B and C `1/8` each.

2. **Row D uses a different methodology.** Cyclicity is measured by *constructive
   generation*: every possible first row is enumerated and the remaining rows generated by
   shifts, with no cyclicity test afterwards. Every matrix produced is cyclic by
   construction and produced exactly once, so the enumerated set **is** `S_R` — a complete
   measurement of 1,024 candidates, not an extrapolation. Under the same
   traverse-and-test methodology as A–C, cyclicity measures **0.235 s**, because the
   traversal must still visit `2^20` blocks and reject 261,888 of every 262,144 on the
   row-0/row-1 prefix. State this wherever the `0.000227 s` figure is used.

3. **Weight-4 carries a sampling correction.** Weight-4 row values are not uniformly
   distributed over contiguous ranges of the row alphabet, so the estimate is scaled by
   `global density / region density = 1.0546875`. Raw uncorrected estimate: 343.15 s. The
   correction is independently validated: it maps both sampled retention fractions
   (0.02320045 and 0.02900057, from 48- and 60-value regions) onto 0.02446920, the exact
   theoretical value.

**On absolute timings.** The published numbers are minima over interleaved repetitions —
the four benchmarks were run in rotation so all saw the same machine conditions. The
machine had intermittent background load (OneDrive sync on the working directory) during
the session, with observed spreads up to 21% on the unconstrained sample. The **ratios**
were stable throughout. For publication-grade absolute runtimes, re-take them on a quiet
machine with the working directory outside any sync folder.

## Fair comparison between engines

For the identity `(T/T_none) / (S_R/S_0) = c_constrained / c_none` to mean anything, the
engines must do the same work per candidate. Three asymmetries were found and removed;
none changed a computed result (every checksum is unchanged):

1. **Tile size** — all engines now process a common tile of 32,768 candidates. Array size
   alone was worth 11% and had pushed the weight-4 ratio *below* `S_R/S_0`.
2. **Operand form** — all engines now use broadcast `(n,1)/(1,n)` operands rather than
   materialised `(405,405)` arrays.
3. **Reduction width** — all engines now reduce in the same integer width.

---

## Validation

Eight invariants are checked, listed in full in `RESULTS_SUMMARY.md`. The important ones:

- Enumerated candidate count equals `S_0` exactly in every traversal run.
- Retention matches the combinatorial `S_R` for all three constraints.
- Each engine accepts matrices that *violate* the constraints it does not impose (weight-4
  accepts a rank-1 matrix and an anticommuting pair; cyclicity accepts the all-zero
  matrix), confirming no hidden rank or commutation test.
- Constructive generation reproduces the filter version exactly: same 1,024 matrices, same
  checksum, same 15 span-mode target occurrences.
- All engines agree with independent brute force at `--work 1, 2, 5` across three toy
  specifications (`--self-test`).

## Running

```bash
cd src
python stabilizer_search_benchmark_weight4.py --n 5 --k 1 --d 3 \
    --constraint weight --weights 4 --backend numpy --target span \
    --work 5 --r0-start 128 --r0-count 128 --repetitions 2

python stabilizer_search_benchmark_cyclic.py --n 5 --k 1 --d 3 \
    --constraint cyclic --mode generate --backend numpy --target span \
    --work 5 --repetitions 200
```

Key flags: `--backend {auto,numpy,pure}`, `--work N` (per-candidate workload), `--target
{span,exact,off}`, `--mode {filter,generate}`, `--r0-start/--r0-count` (sample region),
`--repetitions`, `--self-test`, `--dry-run`.

Reference environment: Python 3.13.7, NumPy 2.5.2.
